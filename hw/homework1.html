Public-Key Cryptography HW1

PRIVATE KEY → PUBLIC KEY in Ethereum

Notes

Elliptic-curve scalar multiplication can be viewed as a one-way function: the forward direction is deterministic and cheap (private key k → public key Q = kG), while recovering k from Q is the Elliptic Curve Discrete Logarithm Problem (ECDLP). It shares some traits with cryptographic hash functions, but it is not a hash: it is used for public-key cryptography and digital signatures.

Ethereum uses the curve secp256k1, y² = x³ + 7 over a 256-bit prime field. The goal here is to understand the idea, not to build a real cryptosystem, so everything below runs on the toy curve y² = x³ + 7 (mod 17) with base point G = (1, 5) and private key k = 6. All parameters can be changed in the controls.

1 · Toy public key: Q = kG

Points are added with the chord-and-tangent rule over the field F₁₇. For P = (x₁, y₁) and Q = (x₂, y₂): the slope is λ = (y₂ − y₁)/(x₂ − x₁) when P ≠ Q, or λ = 3x₁²/(2y₁) when P = Q (the curve has a = 0); then x₃ = λ² − x₁ − x₂ and y₃ = λ(x₁ − x₃) − y₁, everything mod 17. Two points with the same x and opposite y add up to the point at infinity O.

4 · Discussion

What the experiment can and cannot show. Statistics probes the structure of the outputs. It cannot show that inverting k ↦ kG is hard: on the toy curve there are at most 18 candidates for k, and even for p = 65521 a brute-force search is immediate. The hardness of the ECDLP is an assumption that only holds at cryptographic sizes (about 2²⁵⁶ points on secp256k1). Also note that p = 17 satisfies p ≡ 2 (mod 3), which makes y² = x³ + 7 a supersingular curve with p + 1 points, a case that real parameters avoid (secp256k1 has p ≡ 1 (mod 3) and a prime group order).

Properties meaningful for a one-way function.

  • Determinism and an efficient forward computation: double-and-add needs about log₂ k group operations instead of k − 1.
  • Injectivity on k = 1 … n−1: the frequency check shows each point exactly once. If k is uniform, so is the public key over the subgroup, which is what key generation needs (no preferred keys).
  • Hardness of inversion (preimage resistance), which is a computational property and is not measured by any of the tests above.

Properties tied to cryptographic hash functions.

  • Uniform output bits and avalanche. A hash is designed so that its output looks like a random bit string and a one-bit change in the input flips about half of the output bits. An elliptic-curve point is not a random bit string: it satisfies the curve equation, so roughly half of the possible x values never occur and the high-order bits of x and y are biased because the values are smaller than p (visible in the bit charts, strongly for small p). The avalanche figure is measured only to compare; the function was not designed for it.
  • Algebraic structure. Scalar multiplication satisfies (k₁+k₂)G = k₁G + k₂G, as the last test confirms. Consequently Q(k+1) = Q(k) + G is easy to compute from public data, so outputs of neighbouring inputs are related. A hash function must have no such relation.
  • Compression and collision resistance. A hash maps arbitrary-length inputs to a fixed size, so collisions exist and must be hard to find. Here the map is a bijection between k mod n and the subgroup: it does not compress, so collisions in the hash sense do not arise.
  • Correlation between input and output. A correlation close to 0 between k and the coordinates is a weak sanity check (it only detects linear dependence). It does not contradict the strong algebraic relation above.

Ethereum combines both tools: the public key (x‖y) is obtained by scalar multiplication, and the address is then taken from the last 20 bytes of the Keccak-256 hash of that public key. The hash adds the output uniformity and avalanche behaviour that the curve point lacks.
