From Wallet Seed to Ethereum Address

Hashing, key derivation and cryptographic primitives — statistical properties

Notes

An Ethereum wallet turns a list of words into an address through a chain of different primitives. Each step has its own job, and confusing them (for example calling every step “encryption” or “hashing”) hides what is really happening. The page contains: the pipeline and the role of each standard (section 1), a live implementation of every step written from scratch in JavaScript, with no wallet library (section 2), a small tool that compares Keccak-256 and SHA3-256 (section 3), statistical experiments on the outputs (section 4), the historical context (section 5) and a discussion (section 6).

Educational demo: everything runs locally in your browser. Anyone who knows a wallet's mnemonic controls its funds, so use only the example phrase or a brand-new wallet with no funds.
1 · The pipeline and its standards

Mnemonic → BIP-39 → Seed → BIP-32 / BIP-44 → Private key → secp256k1 → Public key → Keccak-256 → Address → EIP-55 → Checksummed address

Step Standard / primitive Input → output Kind of operation
1 · Mnemonic BIP-39 (entropy → words) 128–256 random bits + SHA-256 checksum bits → 12–24 words (11 bits each) key generation (the only random step) + checksum + encoding
2 · Seed BIP-39 (PBKDF2-HMAC-SHA512, 2048 rounds) mnemonic + optional passphrase → 512-bit seed key derivation (key stretching)
3 · Private key BIP-32 (HMAC-SHA512) with a BIP-44 path m/44'/60'/0'/0/0 seed + path → 256-bit private key k (and chain code) hierarchical key derivation
4 · Public key secp256k1, y² = x³ + 7 k → Q = kG = (x ‖ y), 64 bytes public-key cryptography (one-way trapdoor-free map)
5 · Address Keccak-256 64-byte public key → 32-byte digest → last 20 bytes hashing (compression + truncation)
6 · Checksummed address EIP-55 40 hex digits → same digits with letter case chosen from Keccak-256 of the address checksum, expressed as an encoding

BIP-39 gives a human-friendly backup of the randomness, with a built-in error check, and a slow function to stretch it into a seed. BIP-32 makes a whole tree of keys from one seed, so a single backup covers every account. BIP-44 fixes the meaning of the levels of that tree (purpose' / coin type' / account' / change / index; coin type 60 is Ethereum), which lets different wallets find the same accounts. secp256k1 links the private key to the public key and is what makes signatures possible. Keccak-256 shortens and masks the public key into an address. EIP-55 lets a person or a program notice a mistyped address.

Try it with a real wallet (MetaMask, Rabby, Rainbow, Exodus, …): create a new wallet with no funds, write down its 12 words, paste them in section 2 and compare. For MetaMask the first account should match path m/44'/60'/0'/0/0 and the second m/44'/60'/0'/0/1; some wallets vary the account level instead (m/44'/60'/1'/0/0), so changing the path shows how each wallet organizes its accounts.

2 · The pipeline, step by step

All the code of this page implements the steps directly: BIP-39 (word list and checksum), PBKDF2 and HMAC-SHA512 (from the browser's Web Crypto API), BIP-32, secp256k1 point multiplication, Keccak-256 and EIP-55. The default phrase is the well-known test vector, whose first Ethereum address is 0x9858EfFD232B4033E47d90003D41EC34EcaEda94.

3 · Keccak-256 is not SHA3-256

Keccak is the design that won the NIST competition and became SHA-3 (FIPS 202, 2015). Ethereum adopted Keccak-256 before the standard was final. NIST then added a domain-separation suffix to the padding, so the first padding byte is 0x06 in SHA3-256 and 0x01 in Keccak-256. The permutation, the rate and the capacity are identical, but the outputs are unrelated. SHA-2 (here SHA-256 and SHA-512) is a different construction altogether.

4 · Statistical properties

The experiment generates N random mnemonics (seeded generator, so a run can be repeated exactly) and runs the complete pipeline on each. It then measures what a good cryptographic pipeline should show: output bits close to uniform, no correlation between neighbouring inputs and outputs, strong avalanche. A separate test checks how well the EIP-55 checksum detects typing mistakes. Statistics can reveal defects but cannot prove security: a pseudo-random-looking output is necessary, not sufficient.

SHA-2 versus Keccak / SHA-3. Both are cryptographic hash families. SHA-2 chains a compression function over message blocks (Merkle–Damgård), which allows length-extension attacks on the plain hash. Keccak is a sponge: the message is absorbed into a large state through a fixed permutation and the digest is squeezed out, so the hidden capacity part of the state prevents length extension. They are related only by purpose and by NIST's selection process; they share no internal structure. The wallet uses both on purpose: SHA-2 (HMAC-SHA512, PBKDF2, SHA-256) for key management, Keccak-256 for Ethereum's own addresses and hashes.

6 · Discussion

Distinguishing the concepts.

Concept In this pipeline Key properties
Key generation Choosing the random entropy behind the mnemonic The only source of secrecy: all later steps are deterministic. If the randomness is poor, nothing downstream can repair it.
Key derivation PBKDF2 (mnemonic → seed), HMAC-SHA512 (seed → child keys) Deterministic: same input, same keys. Produces many independent-looking keys from one secret, and makes brute force of weak passphrases slower.
Public-key cryptography secp256k1: Q = kG Easy forward, hard to invert (ECDLP); keeps algebraic structure, which is what allows signatures and non-hardened public derivation.
Hashing Keccak-256 (also SHA-256 and SHA-512 inside BIP-39/32) No key, fixed-size output, preimage and collision resistance, avalanche. No algebraic structure is wanted.
Checksums BIP-39 last bits (4 bits for 12 words); EIP-55 letter case Detect accidental errors only. They are not secret and give no protection against an attacker.
Encoding Entropy → words (11 bits per word), bytes → hex, 0x prefix, letter case Reversible change of representation, with no secrecy and no security by itself.

Why several techniques instead of one algorithm. Each primitive solves a different problem, and no single algorithm has all the required properties.

  • BIP-39 / BIP-32 / BIP-44 — key management. One backup must cover many keys, be readable by humans and be recoverable on another device. Hash-like derivation fits this, and a public-key operation would add nothing.
  • secp256k1 — the key relationship. Only a public-key scheme gives a public value from which the private key cannot be found, yet usable to verify signatures. A hash cannot sign, and an elliptic-curve point is not a good compact identifier.
  • Keccak-256 — hashing. It compresses the 64-byte public key to a short identifier, hides the full public key until the first transaction, and behaves like a random function. It cannot derive or sign anything.
  • EIP-55 — error detection. Addresses are typed, copied and read by people. A checksum catches mistakes at almost no cost, without changing the address format that existing software already accepts.

Reading the statistics. The hash-based steps (seed, child keys, address) give outputs that are statistically indistinguishable from random, with avalanche close to one half, as expected. Sequential indices (…/0, …/1, …) give unrelated keys and addresses: knowing one address says nothing about the next. The EIP-55 test shows that the checksum is only about as strong as the number of letters in the address (about 15 on average), so it detects almost every typo but not all of them, and it adds no security against an attacker who can choose the address.
